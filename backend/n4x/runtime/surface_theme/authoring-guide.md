# N4X platform UI authoring guide

1. Applications are backend-only. For any UI, create an `Experience` and draft `ExperienceRevision`, declare its Application access, then call `inspect_experience_design_context` before writing or editing Surface source. Use the returned active guide and theme revisions, content hashes, profile precedence, workflow, and visual-review checklist as runtime authority. The individual `inspect_authoring_guide`, `inspect_surface_theme`, `inspect_component_palette`, and `inspect_experience_bridge` tools remain available for focused inspection.

2. Respect the revision's `ui_profile`. For `n4x-default`, build Experience-owned shadcn/ui components with Tailwind and map their utilities to the active N4X theme tokens. For `custom`, the user-selected design system takes precedence and must not be mixed with the N4X default profile unless the user explicitly requests it. For `none`, the Experience owns its complete visual implementation and the N4X theme and palette are optional.

3. Inspect existing graph SourceFiles before adding UI. Reuse an established component foundation, shell, utilities, and conventions. For a new `n4x-default` Experience, establish the reusable component foundation before broad feature work. Semantic classes such as `bg-card` and `text-muted-foreground` apply theme colors but do not by themselves constitute shadcn/ui composition.

4. For standalone `n4x-default` application chrome, use shadcn/ui `Sidebar` with `variant="inset"` and compose the main surface inside `SidebarInset`. Use the selected component system for buttons, fields, dialogs, sheets, command interfaces, tabs, menus, and other recurring controls instead of accumulating one-off lookalike primitives. This is composition guidance, not a deterministic source restriction.

5. Use only these pinned implementation references:
   - **Dashboard chrome — TweakCN:** URL `https://github.com/jnsahaj/tweakcn/tree/d21c8e3d4071f7f738e46c92470abf9e15bfda04/components/examples/dashboard`; commit `d21c8e3d4071f7f738e46c92470abf9e15bfda04`; license `Apache-2.0`; use for standalone shell composition cues; do not copy branding, navigation, KPIs, charts, tables, labels, or sample data.
   - **Dashboard chrome — shadcn/ui `dashboard-01`:** URL `https://github.com/shadcn-ui/ui/tree/4e88ab81ae1d1550165db949a903c691a04f699c/apps/v4/registry/new-york-v4/blocks/dashboard-01`; commit `4e88ab81ae1d1550165db949a903c691a04f699c`; license `MIT`; use for the `Sidebar variant="inset"` plus `SidebarInset` shell structure; do not copy Acme branding, demo navigation, KPIs, charts, tables, or sample data.
   - **Mail interior — TweakCN:** URL `https://github.com/jnsahaj/tweakcn/tree/d21c8e3d4071f7f738e46c92470abf9e15bfda04/components/examples/mail`; commit `d21c8e3d4071f7f738e46c92470abf9e15bfda04`; license `Apache-2.0`; use for list/detail/compose interaction patterns inside the application shell; do not copy demo accounts, folders, contacts, threads, or messages.
   - **Tasks, Cards, and Typography — TweakCN:** URLs under `https://github.com/jnsahaj/tweakcn/tree/d21c8e3d4071f7f738e46c92470abf9e15bfda04/components/examples`; commit `d21c8e3d4071f7f738e46c92470abf9e15bfda04`; license `Apache-2.0`; use only for optional control, density, grouping, hierarchy, and rhythm cues; do not copy demo records or unsupported actions.
   - **Application, Marketing, and Music — TweakCN:** same pinned examples URL, commit, and `Apache-2.0` license; these are not the default standalone shell. Use them only when the user explicitly requests that kind of experience, and do not copy their demo information architecture.

6. Never copy demo information architecture. Names such as Acme, dashboard KPIs, sample charts, fake threads, placeholder tasks, and example navigation are reference content, not product requirements.

7. Every visible control, count, navigation target, status, and action must map to graph data, an app-scoped read, or an active action. Remove decorative or inert product capabilities that have no runtime implementation.

8. Navigation and local mutations paint before invoke returns. Open the next screen from a query flag, optimistic row, or cached object. Persist in the background. Roll back and toast on failure. Do not await create only to obtain an id, and do not use a global busy for mark, create, or navigate.

9. Build changed Surfaces incrementally. When browser capability is available, capture and inspect screenshots for every changed Surface in the relevant desktop, narrow, light, and dark states. Review hierarchy, density, typography, spacing, overflow, interaction states, and contrast. If a relevant state cannot be inspected, report that limitation before validation or activation. Compilation and structural validation do not establish visual quality.

10. Use only `n4x.experience.bridge.v1` from `inspect_experience_bridge`. Browser Surfaces are served below `/experience/{experience_id}` and use the declared Application capability routes below `/api/experiences/{experience_id}/apps/{application_id}`. MCP App Surfaces call their app-only tools through the standard `window.parent.postMessage` JSON-RPC `tools/call` bridge; `window.openai.callTool` is an optional compatibility fallback. Never use `/api/apps/...` from Surface code; those routes are trusted host APIs. A missing definition allowlist permits all active definitions in the declared Application, while an empty allowlist permits none. Secret-reference access is stricter: missing and empty both deny.

11. Treat this guide as advisory design authority, not as a UI validator. Use `validate_experience_revision` separately for Application access, source, dependency, and Surface structure before activation. N4X does not assign pass/fail design judgments.

12. Progressive Web App installability is opt-in on the Experience's `/` browser Surface (`config.pwa: {}`, default artifact `manifest.webmanifest`). There is no `kind: pwa` and no convert-Experience tool. Same product that should remain one installed app: create a new Experience revision, set `pwa: {}` on the `/` browser Surface, add the web manifest and a `<link rel="manifest">` in HTML, optionally `sw.js` plus `navigator.serviceWorker.register()`, then activate. New product identity (different name, icon, URL, or allowlist): `create_experience`, then the same Surface opt-in. Desktop vs mobile is responsive layout in that Experience, not a second Experience. MCP App Surfaces are not installable. The host binds `start_url`, `scope`, and `id` to the live Experience URL; keep other manifest members in Experience source.
